# 多巴胺口算 — 设计与落地方案

**状态：设计稿，尚未实现。** 本文描述两项计划中的功能——无尽模式、成长页与错因归因——的设计与接入方案。

游戏当前**已实现**的行为见 `docs/SPEC.md`；本文与它冲突时，`docs/SPEC.md` 描述现状，本文描述目标。文中标注「现状」的部分是对现有代码的核实结果，可直接对照；标注「方案」的部分尚未动工。

---

## 0. 两条硬约束

### 0.1 存档版本号不可更动

`app/js/store.js` 的 `load()` 只在版本号一致时读取存档：

```js
if (data && data.version === VERSION) { ...读取... }
```

版本不匹配时会**丢弃整个存档、以初始状态启动**。而新增字段本来就不需要动版本号：

- `load()` 末尾有 `for (const [k, v] of Object.entries(data)) if (!(k in base)) base[k] = v`
- `progress`、`stats`、`trophies`、`items`、`quests` 等状态都是在访问时惰性创建的

因此本方案的所有新数据一律**惰性创建 + 缺省容错**，`VERSION` 保持 `1` 不动。做错这一步会清空所有用户的星星、奖杯与记录，且不可恢复。

### 0.2 界面文案的成本是「×3 语言 + 一次字体重建」

- `tools/check-i18n.mjs` 强制每个键在 en / ja 两个包里都有条目（当前 556 个键）
- `tools/build_fonts.mjs` 按**实际用到的字符**生成中文字体子集。新文案里不在子集内的字符会掉到 fallback 字形，在同屏中一眼可见

新增文案必须**在设计阶段定稿、集中加入**，避免反复重建字体子集。已实测的字形影响见 §2.6。

## 1. 已确认的设计决定

以下决定已经过讨论确认，记录在此以免重复讨论。

### 1.1 保留「我的等级」，不替换为无尽模式

「我的等级」不是一个模式，而是三件别处没有的事：

| 职责 | 实现 | 无尽模式为何不能替代 |
| --- | --- | --- |
| 实力测试 | `placementPlan` + `walk` 升降梯；一次答对即把该技能及其前置一并标记掌握并给 ☆1 | 无尽没有容纳一次性诊断的位置 |
| 前沿选题 | 按前置深度重复「已解锁・未掌握的前 4 个技能」 | 无尽按年级递增，是「奖励已会的」，方向相反 |
| 复习调度 | `min(候选数, max(1, round(题数 × 0.3)))`，生锈优先 | 全 app 唯一的强制复习机制，无尽不带 |

另外，标题页的 `#level-sub` 已经在预告下一步（「接下来是「四位数加法竖式」」），它已经是教练行为，不是盲盒。

**同时**：连胜、每日任务、日历的「当日最高分」、奖杯的「练习次数／时间」都建立在有界的一局（6/10/14 题、100 分制）之上。替换主入口需要重新定义「练了一局」的口径，属于重做每日指标，不是改一个按钮。

### 1.2 结算页不承接无尽

无尽模式**不从结算页进入**，只有标题页一个入口。由此产生三点：

- 它与「加时挑战」的关系反而清晰了：加时挑战是**结算后达标的追加回合（奖励）**，无尽是**上桌前选定的模式（意图）**，两者不再重叠。加时挑战及其关联的 5 个收藏解锁、3 个奖杯系列全部保留。
- 无尽需要**自己的结算页**，且是终点页（按钮只有「再来一次」「返回标题」），不复用加时挑战的按钮逻辑。
- 发现路径要自己承担，见 §2.7.4。

### 1.3 成长页定名为「成长」

| 项 | 值 |
| --- | --- |
| zh | 成长 |
| en | `Growth`（语言包已有） |
| ja | `せいちょう`（语言包已有） |

不叫「家长视图」：那会让这一页变成「一份关于我的报告，给别人看」，与全 app 刻意非惩罚性的设计语言相悖。也不叫「统计」：项目内部本来就用「成长」称呼这件事——`app/js/growth.js` 的首行注释是 `// Lifetime statistics`，奖杯有一个「成长」分类（擦亮生锈／时间胶囊／比那天更快／进步啦！）。「成长」读起来是孩子自己的进步，可以拿给家长看，而不是被家长查。

zh 的 `成长` 两个字符已在字体子集内，en / ja 的译法也已存在，**这个标签本身零成本**。

### 1.4 明确不做的事

| 不做 | 理由 |
| --- | --- |
| 排行榜、社交比较、好友 | 与「无账号、不联网」的定位冲突；自我参照对孩子更健康 |
| 抽签、内购 | 现有原则：奖励全部由达成条件解锁 |
| 断签惩罚、失败扣星 | 现有原则：已获得的不会因失败或缺席被收回 |
| 家长权限、密码、隐藏入口 | 一旦孩子觉得有东西在背着他记录，信任就没了 |
| 周报推送、提醒、通知 | 要看得自己打开 |
| 替换「我的等级」 | 见 §1.1 |
| **体力／精力系统** | 见 §1.5。在没有内购的产品里它只剩惩罚，且与五条既有原则冲突 |

### 1.5 为什么不做体力（精力）系统

曾考虑过「每天 5 点体力」的方案，目的是防止答题随意退出。结论是不做，理由如下。

**一、今天退出已经有代价。** 实测各处的写入时机：

| 数据 | 写入时机 | 中途退出 |
| --- | --- | --- |
| 每题熟练度、星星 | `recordResult`，每题结算时 | **保留** |
| 错题进复习队列 | `noteProblem`，每题结算时 | **保留** |
| 本局历史记录（分数／用时） | `addRecord`，结算页 | 丢失 |
| 100 分与结算页奖励 | 结算页 | 丢失 |
| 当天计入「练习日」 | 依赖 `history[].day` | **丢失 → 当天不计入连续天数** |

随手退出已经会丢掉当天的连续天数。这是「你没练完」的自然结果，不是人为门槛。

**二、它与已有的五条原则正面冲突。** 逐条对照 `docs/SPEC.md`：

1. 「基础题超时也能继续，做完全部即 100 分，**没有游戏结束**」
2. 「已获得的星星、奖杯和演出**不会因失败或缺席被收回**」
3. 「答错会提示『差一点』，**可以重新输入**」——错误从不带惩罚
4. 「奖励全部由达成条件解锁，**没有抽签和内购**」
5. 补签锤的定位是「**帮孩子接上**」，而不是「让他怕断」

体力是第六种东西：纯粹的惩罚。而正是因为第 4 条，**体力失去了它的原始功能**——在免费游戏里它是「限制游玩 + 卖补充」的前半截，去掉后半截就只剩限制。

**三、它会抵消刚做完的设计。** 做题界面的返回键特意走确认框（提交信息：「误触不应该丢掉一局」）。体力会让「离开」重新变贵，正好抵消这一点。

**四、它惩罚最该被允许停下的时刻。** 累了、烦了、被叫走了就停下，是需要培养的自我调节能力。家长喊吃饭、来电话、想上厕所都不该收费。

**五、五点上限会精准卡住最投入的孩子。** 一局约 3 分钟，5 局约 15–25 分钟；普通使用碰不到上限，被卡住的是想多玩几局的那个。

**六、观感。** 家长看到「体力 0/5，明天再来」会直接读成手游套路，与「专业、诚实、不联网、无内购」的定位相悖。

**它也不解决成因。** 若真正的担心是「遇到难题就退」，体力只会让继续下去的代价更高，退出的动机更强。按目标不同，更对症的做法：

| 担心的情况 | 更合适的做法 |
| --- | --- |
| 遇难题就退（逃避） | 这是难度问题。先确认发生在哪个模式——「按年级」是单一技能、最易腻和卡；「我的等级」带复习配额与前沿选题，最不易卡。**若在按年级观察到，就修那个模式的节奏，不要全局加惩罚** |
| 被打断（电话、家长、走开） | **续玩**：把未完成的一局存下来下次接着做，把「退出＝丢掉」改成「退出＝暂停」。题目对象本就可序列化（复习队列已在存 `stripProblem(p)`） |
| 随手点错退了 | 确认框已解决 |
| 玩太久 | 用温和边界：做完当日三个任务就是自然的「今天够了」；或让多巴奇在若干局后提议休息，不带惩罚 |
| 一局太长坐不住 | 设置里已有 6/10/14，**给容易分心的孩子用 6 题**比加体力更直接 |

**最推荐的低成本替代**：把确认框里的话说具体。现在只写「本次练习将在此结束。」，改为显示当前进度：

> 已经答对 6 题了，再做 4 题就完成。

这是信息而非惩罚，且出现在做决定的那一刻。改动极小，语气与全 app 一致。

**如果将来仍要加**，需要一并决策的比实现更麻烦：每日重置走日期、显示位、耗尽状态文案，以及**每个模式的口径**——复习扣不扣？加时挑战扣不扣？无尽模式扣不扣？（扣，等于给旗舰玩法上锁；不扣，孩子会全去玩无尽，体力对主模式形同虚设。）

## 2. 无尽模式

### 2.1 定位

> **已实现**（阶段 3，`9e2df76`；规则在 `app/js/endless.js`，13 项测试）。两处实施偏差与四个实现期发现的 bug，见 §2.10。

一条命制长跑：难度与演出持续上升，直到命尽。它的作用有两个——一是提供现有模式缺的「再来一次」冲动，二是给演出升级设计一个**足够长的舞台**，让它能跑到设计的峰值。

### 2.2 规则

| 项 | 设计 | 说明 |
| --- | --- | --- |
| 模式标识 | `S.mode = 'endless'`，`plan.mode = 'endless'` | 与现有命名一致 |
| 命数 | 3 条，**错一格扣 1 条** | 不是错一题 |
| 回命 | 每答对 10 题回 1 条，上限 3 | 防止一次手滑终结长跑 |
| 单格时限 | 沿用 `comboWindowMs(grade, first)` | 超时**不扣命**，只断连击——保持现有温和语义 |
| 升波条件 | **一次答对**才计入升波 | 见 §2.4，这是防止「乱猜冲关」的关键 |
| 结束 | 命尽 → 结算 | |
| 放弃 | 现有返回键 + 「返回标题？」确认框 | 复用，无新逻辑 |

`firstTrySolved`（用于升波）与 `solved`（用于回命）必须分开计数。

### 2.3 出题计划：plan 抽象的扩展

**现状**：`plan.basic` 是长度 `N` 的固定数组，`nextProblem(i)` 取 `plan.basic[i]`。无尽模式长度不定，无法用固定数组表达。

**方案**：给 plan 增加可选的 `skillAt(i)`，`nextProblem` 优先使用：

```
nextProblem(i):
  if (plan.mode === 'review')  → 复现保存的题目
  if (plan.legacy)             → 旧 drill 模式
  if (plan.skillAt)            → sessionProblem(plan.skillAt(i))    ← 新增分支
  → 原有逻辑
```

这样现有四种模式（level／grade／practice／review）**一行都不用改**，也不产生 `if (mode === 'endless')` 的分支扩散。

无尽模式的 plan：

```js
{ mode: 'endless', skillAt(i) { ... }, extra: null }
```

`skillAt(i)` 内部维护 `i → 波次 → 年级` 的映射，技能选择复用 `session.js` 现有的 `stateOf` / `frontier` / `rustyOf`。

### 2.4 难度曲线：用课纲当阶梯

```
波次  w = floor(firstTrySolved / 5) + 1      // 每 5 道一次答对升一波
年级  g = min(6, 1 + floor((w − 1) / 2))     // 1-2 波 1 年级，3-4 波 2 年级 …
```

- 第 1–2 波：1 年级技能；第 3–4 波：2 年级；……第 11 波起：6 年级
- 6 年级之后不再升年级，改为**交错混合**：从全部已解锁技能中抽取，并对 `rustyOf()` 与未掌握技能加权
- 升波只用一次答对：这样「打得更远」等价于「算得更准」，而不是「猜得更快」

设计意图：难度上升来自**出题范围**而非单纯加速。打到第 10 波直观地等于在做六年级的题——街机外壳里装的是课纲进度。

### 2.5 数值设计

#### 2.5.1 多巴：换成不收敛曲线

**现状**：`extraDopaL(n) = 2.3 + 3.0 × (1 − e^(−n/10))` 渐近于 5.3，一局到不了「兆」。而 `app/js/scoring.js` 的单位表列到**无量大数（10^68）**，并实现了 兆／京／垓／秭／穰／沟／涧／正／载／极…… 的显示——这张表的存在说明它当初就是为更长的跑法设计的。

**方案**：替换为对数增长，永不收敛。**已实现（阶段 5）**，最终参数与初稿不同：

```
X(n) = c × ln(1 + n / k)              c = 1.2, k = 2
逐格增量 = (X(k+1) − X(k)) / m        与现有 extraProblemGain 同构
```

`c` 从 3.3 降到 1.2 是平衡调整的结果，见下面「单位节奏」一节。

**关键修正**：`X` 是**这一局的累计值**，不是叠加在基础曲线上的偏移。初稿写成 `a + c × ln(1 + n / k)`（`a = 2.3`）再按差分累加——差分会把 `a` 抵消掉，于是屏幕上真正显示的数字比 `X(n)` 低 2.3，而单元测试读的正是 `X(n)` 本身：**测试通过、数字不对**，80 题跑到 600 亿而不是兆。现在 `X(0) = 0`，玩家看到的数就是 `X(n)`，测试也改成「一题一题按 `addDopa` 累加」来验证。这个 bug 是浏览器里真跑一局看数字才现形的。

初稿两组候选与两次实调的对比（无连击累计值，对数）：

| 参数 | 30 题 | 60 题 | 80 题 | 120 题 |
| --- | --- | --- | --- | --- |
| `c=3.6, k=12`（初稿候选 A） | 3.5 | 6.3 | 7.2 | 8.4 |
| `c=4.5, k=8`（初稿候选 B） | 7.0 | 9.6 | 10.8 | 12.5 |
| `c=3.3, k=2`（首版实装，已被取代） | 9.3 | 11.3 | 12.3 | 13.6 |
| **`c=1.2, k=2`（当前）** | **2.6** | **4.3** | **5.0** | **5.9** |

**单位节奏（当前 `c = 1.2`）**。有连击的那一列才是玩家实际遇到的：倍率在第 20 格满 ×2 后不再变化，`playOf` 按格累加；无连击一列把倍率钉在 1.05（第一格永远有这一档）。

| 单位 | 有连击（每题约 2 格） | 无连击 |
| --- | --- | --- |
| 万 | 第 17 题 | 第 46 题 |
| 亿 | 第 96 题 | 第 819 题 |
| 兆 | 第 388 题 | 第 2089 题 |
| 京 | 第 721 题 | 第 3359 题 |
| 垓 | 第 1054 题 | — |

有连击时的一局长度观感：60 题 ≈ 830 万、300 题 ≈ 899 亿、400 题 ≈ 1.4 兆。上限 10^30 要 1888 题才碰到，是纯兜底。

**实测比这张表再慢约一成**——模型假设每题 2 格，实战里常有 3 格题，而一道题的增益要摊到它的每一格上、按当时的倍率结算，格数越多前半段越吃亏。浏览器里真跑的一局（不失手，109 题，第 22 波，第 16 档）：万 第 19 题、亿 第 106 题（模型 17 与 96），`L` 从 0 一路到 8.11。按这个偏差，兆 大约在第 430 题前后。

**这次调整放弃了原定的「60～80 题摸到兆」。** 首版 `c = 3.3` 实测（浏览器里真跑一局不失手，60 题）是 万 第 4 题、亿 第 11 题、兆 第 22 题、京 第 41 题、终局 320 京——比目标快约三倍，于是 `c` 先试 1.7、再定 1.2。现在的代价是明确的：**兆 需要约 390～430 题不失手，多数玩家不会看到 兆 以上的单位**，单位表的上半段回到「装饰」的身份。换来的是单位节奏从「一局换五次」变成「一局一两次」，`unitSlam` 的里程碑演出重新变得稀有。若之后觉得太慢，`c = 2.0` 把 兆 放回第 68 题（有连击）。

配套：

- 该模式**解除 `DOPA_MAX_L = 9.08`**，改用 `ENDLESS_DOPA_MAX_L = 30`；`addDopa` 的封顶改为参数，由模式传入
- 上限是**兜底而不是目标**：满连击跑 120 题也只到 27，够不着 30。一个「好跑法能撞到的上限」正是这条曲线要避免的饱和
- **连击倍率保持 ×2 不变**。长跑中它乘的是每格增量，价值被自然放大
- `unitSlam` 里程碑演出（万→十万→百万→千万→亿→…）成为长跑中的**主要奖励节奏**。这部分代码已经写好，只是一直没有机会展示

#### 2.5.2 分数

沿用 `extraPoints(k) = 10 + 5k` 累加，不设上限。100 题合计 25,750 分。

**与基础模式分开记录**，避免冲淡日历的「当日最高分」（见 §2.8）。

#### 2.5.3 演出等级与阶梯扩展（必须配套）

**现状核实**：

| 项 | 现状 |
| --- | --- |
| `applyLevel` | `L = min(10, round(E × 10))` |
| 基础模式 | E 从 0.08 升到 1.0，L 刚好用满到 10 |
| 加时挑战 | `E = 1 + min(0.5, tier × 0.1)` → **L 全程钉在 10** |
| CSS | `body.lvN` 只定义到 **lv9** |
| 音乐 | `scheduleStep` 的分层阈值只到 **L ≥ 9** |

也就是说 **L=10 之后没有阶梯**。仅加一个无尽模式而不扩阶梯，画面在第 11 题之后就停止变化——玩家会在最需要反馈的时候失去反馈。

**方案（已实现）**：把「此刻多大声」和「爬到第几档」拆成两个数。`E` 继续只表示当下的强度并被限制在演出引擎画得好的区间；等级 `L` 由模式自己命名。

```
E = 1 + (E_MAX − 1) × (1 − e^(−(w−1)/9))     E_MAX = 1.6     // 第 1 波 1.0，第 20 波 1.53
tier = min(16, 10 + floor((w − 1) / 2))                      // 每 2 波升 1 档
L = min(16, round(tier))   // 无尽模式；其他模式仍是 round(E × 10)
```

初稿让 `E` 一路爬到 7（`1 + min(6, 0.18w)`）再由它推出 `L`，这在两端都错：`L` 在第 5 波就被顶到上限，而第 33 波的 `E = 7` 会把 48 发烟花、230 颗雨滴和 4000px/s 的粒子速度交给 `fx`——那是一局里 `fx` 从没被验证过的负载。现在 `E` 有界，长跑的那部分交给 `L`：**`E` 说这一刻多热闹，`L` 说这场演出进行到哪里。**

**四个只有实测才会发现的问题：**

1. **多巴曲线的一个数量级错误**（§2.5.1）。单元测试断言的是曲线值，而玩家看到的是差分的和——两个数差一个常数。浏览器里跑一局、把 `#dopa` 的文本读出来，才看见 80 题停在 600 亿。教训：**测那个被显示的量**，不是测产生它的中间函数。测试因此改成按 `addDopa` 一题一题累加。
2. **`body.lv10 .spot` 把第 12 档的灯也点亮了**。`.spot` 同时匹配两对聚光灯，而第 12 档的全部内容就是第二对——于是第 12 档上线后什么都没发生。
3. **同一类问题的第二次**：`body.lv5 .spot` 从第 5 档起就点亮了第二对，所以第 12 档甚至连「从无到有」都不是，只是把不透明度从 .7 抬到 .85。两次都靠**逐档读回 `getComputedStyle` 的不透明度**才发现，光看截图看不出来（两个数都是「亮着」）。
4. **第 16 档在静音时不存在**。它原本只有 `opacity: calc(var(--kick) * .32)`，而 `--kick` 在音乐未播放或静音时恒为 0——一个只有听着音乐的玩家才看得见的档位。现在有 0.09 的底值。

前两条与第三条是同一类：**CSS 的级联范围比意图宽**。`body.lvN .x` 里的 `.x` 若是个父类，就会连带点亮后来档位拥有的子元素。测试从「这一档有规则」升级为「这一档点名了自己拥有的那一件，且没有用裸选择器」。

**实测覆盖到哪里**。浏览器面板不可见时 Chromium 冻结 rAF，而本应用的游戏时钟、`wait()`／`tween()` 与整个题循环都挂在 rAF 上——这正是阶段 1 实现的「切到后台自动暂停」，所以第一次尝试驱动对局时它停在第 5 题不动，`#clock` 冻在 0:16。

`tools/serve.mjs` 的 `?pump=1`（用 MessageChannel 泵帧）就是为这种情况准备的，接上之后完成了**一整局真实对局**：

- 一局不失手跑到第 16 档：第 10/11/12/13/14/15 档分别在第 9/19/29/39/49/59 题到达（每 10 题一档，正是 `WAVES_PER_TIER = 2` 的 5 次一次答对），第 16 档在第 13 波第 60 题——**第 13 波**正是 `tierOf` 的上限
- 观众在 13 档由 4 位变 6 位（`ensureCrowd(13)` 的第三排）
- `E` 在第 13 波为 1.44，与 `1 + 0.6 × (1 − e^(−12/9))` 一致；`__frame_errs` 与 `__rafErrs` 全程为空
- 多巴实测：万 第 4 题、亿 第 11 题、兆 第 22 题、京 第 41 题、终局 320 京

另外逐档读回了计算样式（`getComputedStyle`），确认每一档都恰好点亮自己那件东西。**仍需真机确认的**只有手感本身：「这一档够不够爽」、「60 题里换 6 次装饰是不是太频繁」这类判断，自动化测试替不了。

### 2.12 无尽模式的收藏与奖杯（id046，已实现）

**发现的缺口**：无尽模式有 12 个奖杯，却**一件收藏都不解锁**；全站 47 件收藏里 39 件是奖杯奖励，而其中没有一件来自无尽。加时挑战能刷出背景、颜色、谢幕，无尽跑到第 30 波什么都不给。原因是 id045 那一批奖励做在无尽模式之前。

**两条必须先知道的硬约束**（读代码才发现，都写进了设计）：

1. **一个奖杯只给一件收藏**。`unlocks.js` 是 `TROPHY[it.trophy].reward = it.id`——单个字段。两件挂同一个奖杯，第二件会静默覆盖第一件。现有 39 件对 39 个不同奖杯，且已有测试守着（`no trophy gives two`）。
2. **「收藏」系列的最后一级就是总件数**（steps 末尾的 47）。新增件必须同时改这一级，否则「集齐全部」永远达不成。

**奖杯：补三个系列**（无尽从 2 系列 12 个变成 5 系列 29 个）

| 系列 | 指标 | 分级 | 回答的问题 |
| --- | --- | --- | --- |
| 无尽局数 | `endlessRuns`（本来就在统计里，一直没人用） | 1、3、10、30、100、300 | 有没有来玩 |
| 单局答对 | 历史里单局 `count` 最大值 | 10、20、30、50、80、120 | 一局能撑多久（与波次不同轴：可以题多波低） |
| 零失误到第几波 | `firstRate === 1` 的局中 `endlessWave` 最大值 | 2、3、5、8、12 | 无错**且**够深 |

后两个指标**扫 history 得出，不新增存档字段**——照 `extraBest` 的先例（`growth.js:31`），因此没有碰 `store` 的 VERSION。可达性对着实测校过：不失手一局 60 题＝第 13 波，所以「单局 120 题」≈第 25 波，与现有「最高 30 波」同量级；「零失误到第 12 波」＝连续 55 题全对；最低档（连续 5 题不错）第一局就能拿。

顺带把**「多巴」系列从 `[2..9]` 扩到 `[…10, 12, 16]`**：10 以上只有无尽够得到，`bestDopaL` 早就在统计里，零成本。

### 2.13 无尽奖励的第一次修订（id046，已实现）

第一版做完之后逐项看实物提出的三处问题，都是「设计上对、看起来不对」：

**1. 收藏页有 3 个分类根本点不到。** 标签条是 `overflow-x: auto` + `scrollbar-width: none` 的隐藏横向滚动条：触摸能滑，但**滚轮与鼠标拖动都滚不动**（实测 `scrollLeft` 恒为 0），于是多巴奇的颜色／观众／谢幕三类在桌面端打不开——而满座与落幕正好在这两类里。改成两行（`flex-wrap: wrap`）并把最长的两个标签换成短名（「标记」「颜色」，页面顶部的横幅本来就写着全名），320px 也不用滚。测试里加了一条守住「必须换行、不得依赖横向滚动」的断言。

**2. 浪花与深浪与其余不搭。** 实测依据：浪花 4 个颜色里 2 个与「泡泡」完全相同（#bfeaff、#d9f7ff）却是硬描边曲线；深浪基色 L9/S83，比夜空（L20/S48）、宇宙（L11/S70）都更暗更饱和，而其他深色主题都把深色配紫。

- **浪花 → 星星**：改成五角星（#ffd23f 描墨线 + 少量白星），与「烟花环」标记同族。主题键取 `twinkle` 而不是 `star`——爆发里本来就有一种叫 `star` 的粒子，而 `THEME_DRAW` 先于那条 switch 被查，叫 `star` 的主题会把所有爆发的星星一起改掉。
- **深浪 → 光阶**：五道升起的彩色光阶，随等级逐级点亮，顶阶是奶油色；基底是墨色 #1b1d4d → 大海的蓝 #2a6fb8（夜空自己的明度/饱和度区间），并把该主题的节拍泛白从 .34 降到 .16，否则它也被推成浅色。

**两个只有量像素才会发现的坑**（都发生在这一段）：

- **背景的坐标以卡片为中心**：`p = (fc − uCenter)/uRes.y`，而 `uCenter` 是卡片/多巴奇的中心（本例 y = 240）。于是可见的背景带是 `p.y ≈ −0.29…+0.19`，我按 `p.y ∈ [−0.4, 0.44]` 摆的阶梯正好落在卡片与键盘**后面**，第一版根本没显形。改成 `−0.24…+0.18`。
- **`smoothstep` 的边界写反是未定义行为**：阶梯的 `on = smoothstep(fi + .75, fi + .15, E * 4.6)`（降序）在本驱动上被读成 0，于是**五道彩色阶梯的权重全为零**，只有用升序写的奶油顶阶亮着——扫描一行像素时看到「一条亮带 + 一片平滑渐变」才定位到。新写的取值一律改成升序形式。既有主题里大量使用降序 smoothstep，在本驱动上工作正常，但这属于同一处未定义行为，值得单独记一笔。

**3. 月桂冠与皇冠分不开，落幕不像台口。** 月桂冠原本与皇冠同为金色、同在头顶附近，在 0.46 倍观众身上都是一坨金 → 改成**绿叶 + 金扎带 + 红结**（叶子放大 20%）。落幕本来只是两块布推进来 → 加上**波浪檐幕**（顶部台口）、每半边的**束腰与金色流苏**、地面光斑。

**4. 无尽与电子乐同和声。** 客观对照：无尽原本的进行是 Am–F–C–G，**与电子乐完全相同**，16 个声部里 8 个重合（kick/clap/hat/sub/pluck/pad/impact/snare），1–6 档的配方几乎同构。改成 **Am–G–F–E**（根音 9,7,5,4——六首曲子里唯一用到 4 的），贝斯每小节下行一级；`sub` 换成 `glock`，主声部落在 bell／glock／choir 上。改后共有声部降到 7 个且全是通用打击与键盘，独有声部 8 个。

字号层面：三语各 +2（标记／颜色）−2（浪花／深浪）键，字体子集随之重建（**新增 阶，移除 浪 深**，无缺字）。

### 2.14 光阶的第二稿与收藏页的预览曝光（id046，已实现）

**「切换别的分类后光阶不见了」不是状态被清掉**：实测选完光阶再切到装扮类点物品，`bg.state.theme` 仍是 6、`S.look.bg` 仍是 `bg:steps`。真正发生的是**曝光**：收藏页里只有「背景」类会把 `S.previewE` 补间到 1.1，其他类固定 0.3，而着色器的 alpha 曲线在 0.3 处正好是 **0.32**——五种背景在这个曝光下都被洗成一片（实测可见区亮度极差 1.9–9.2 / 255）。所以「消失」是所有背景共有的，只是刚看满亮的那个落差最大。

三处修正：

| 改动 | 依据 |
| --- | --- |
| `PREVIEW_E = 0.55`（一处常量，`openCollection` 与 `previewItem` 共用） | 该曝光下五种背景的极差升到 41–165 |
| 背景预览的曝光补间加 token，下一次预览即失效 | 原本它会继续写 1.4 秒：选完背景立刻点别的类，`previewE` 会停在 1.1 |
| 着色器新增 `uFloor`，`showScreen('collect')` 时设为 `PREVIEW_E` | 任何屏幕都不该把背景洗到看不见 |

**光阶重画了三稿**，两稿都因为「量了才发现」的问题作废：

1. 第一稿是水平色带 + 硬边、颜色只以 42% 混入 → 实测亮带取样是 `(90,183,185)` 这类中间色（不绚丽），形状也只有一种元素（粗糙）。
2. 第二稿改成「对角阶梯」→ 截图与扫描都显示是**斜向光带**而不是台阶：踏面本身倾斜，就没有台阶的读法。
3. 第三稿把踏面改成水平、用**逐级右移的端点**表达上升（端点全部落在画面内），加**立面**（每级右端的竖直落差）、收紧光晕——第二稿的光晕扩散约 46px 而级距 81px，五级光晕互相重叠糊成色带，这是它读不出台阶的直接原因。

最终形态：六块水平的踏面，每块有亮顶边、紧凑光晕（`exp(-|d|×70)`）、右端竖直立面，颜色直接取调色板五色（不再用 `hsv` 的中间色），未点亮的阶以暗剪影存在（所以低等级也看得出形状），另加浮尘与地面光池。亮度剖面在 x=40 处有五个间隔 81px 的峰（74/158/241/410 等），与设计一致。

**一个几乎漏掉的破坏性错误**：第二稿的区块替换把 `space` 主题整段吃掉了，而分发仍调用它——着色器编译失败，`bg.js` 捕获后把 `gl` 置空、背景整片消失。是「先验证 `bg.gl` 非空」这一步抓到的（`bg.gl` 为 null 就等于编译失败，因为 init 会把异常吞掉只留一条 console 警告）。着色器任何改动之后的第一件事都应该是这个检查。

## 3. 成长页与错因归因

### 3.1 错因归因引擎（先采集，后展示）

#### 3.1.1 采集点

`onWrong(cell, st)` 是**唯一同时掌握「步骤定义」与「玩家按下的数字」的地方**。现有代码就在此处：

```js
carry(from, cell, key, () => { cell.classList.remove('pending'); onWrong(cell, st); });
```

注意 `key` 目前没有传入 `onWrong`，需要加一个参数。**归因必须当场判定**——事后无法重建「孩子按了哪个数字」。

#### 3.1.2 判据

> **已实现**（阶段 1）。以下是实现后的实际情况，与初稿有三处出入，都已按实测修正：判据由 8 条收敛为 5 条可证伪的；横式题单独处理；`label` 与 `carryFrom` 最终没有用上（`help.ids` 与 `marks` 的信息更可靠）。

`app/js/problems.js` 的生成器产出的步骤对象已含所需信息：

| 字段 | 内容 | 用途 |
| --- | --- | --- |
| `help.ids` | 参照格 id（含进位格 `k7`；列的 id 形如 `a/b/k/p/q/m`） | 判断进位是否参与，并区分竖式与横式 |
| `help.text` | 孩子本该做的算式（如 `"7 ＋ 8 ＋ 1"`），或一句概念提示 | 复算，看按下的数字是否等于某个特定错法的结果 |
| `marks` | 减法的退位链（跨零时会出现 `9`） | 跨零退位判定 |
| `digit` | 正确数字 | 比对 |

分类函数是纯函数，位于 `app/js/slips.js`：

```js
classifySlip(step, typed, problem) → causeId | null
```

**只在这五条成立时归因，其余一律 `unclassified`：**

| causeId | 判据 | 例 |
| --- | --- | --- |
| `carry` | 该位存在进位，且 typed == 忽略它的结果 | 该做 7+8+1=16 写 6，按了 5（= 7+8 的个位） |
| `borrowZero` | `marks` 里出现 `9`（借位穿过了 0）且该步答错 | 700−274 的十位 |
| `borrowMiss` | 该列发生了退位，且 typed == 把小的从大的里减的结果 | 该写 12−7=5，按了 7−2 的读法 |
| `swap` | `label` 形如 `乘{n}`，且 typed == 积的十位数字 | 7×8=56 该写 6，按了 5 |
| `wrongFactor` | typed == 用另一个乘数位相乘的个位 | 用错了乘数的另一位 |

**识别列运算靠 cell id，不靠措辞。** 只有列结构生成器（`buildAdd` / `buildSub` / `buildMul` / `buildDiv`）产出的是列算式；其余技能的 `help` 是给孩子的概念提示（`分母乘分母，分子乘分子`、`将十位四舍五入`、`5的口诀 5 10 15 …`），没有可复算的算式，因此那些步骤**按设计不归因**。用 id 前缀区分竖式（`a/b/k/p/q/m`）与横式（`g/x/w/d`）。

**横式题单独处理。** 横式（`buildH`）每步对应答案的一位数字，而 `help` 是整题的提示——那里 `"20 − 10"` 就是题目本身，不是某一列。所以横式改为从表达式重算，并且**要归因的进位是"从右边进上来的"那个**：`8 + 5 = 13` 的十位 1 就是进位，写 0 即是丢掉它。

**尚未检测（按设计落入 `unclassified`）：** 部分积的数位错位、商的估算、小数点位置、输入顺序、乘法口诀的"差一行"、三位数连算的中间结果。每条都需要一个对整列成立、而非只对一个数字成立的判据，靠猜会破坏上面那条原则。

**实测覆盖率**（58 个技能 × 25 题，共 4003 个步骤）：

| 指标 | 数值 |
| --- | --- |
| 可解析为算式 | 1760 / 4003 = **44.0%** |
| 其中至少一种错误可归因 | 963 / 4003 = **24.1%** |
| 一年级六个进位／退位技能 | **100%** |

后一个数字低于前一个是正常的：没有进位的普通列，任何错数字都只是"错"，没有可证伪的错误模式。**这两个数字是步骤维度的；§4 阶段 1 的验收标准是真实错答的归因占比，口径不同，需要在真实使用中另测。**


**原则：只在按下数字与推定的错误算法完全一致时才归类，否则一律落到 `unclassified`。** 专业报告里写错诊断比不写更伤信任。

#### 3.1.3 存储

> **已实现**。

```
prog.skills[id].slips    = { carry: 3, borrowZero: 1, unclassified: 2, … }
prog.skills[id].slipDays = { '2026-10-10': { carry: 2 }, … }   // 保留 30 天
```

- 惰性创建，**不动 VERSION**（`session.js` 为此导出了 `skillRecord`，让归因能在该技能第一道题完成之前就有地方写）
- 未归因的错答也计数（键名 `unclassified`），这样报告能显示「已归因 N 次 / 共 M 次」
- `slipDays` 保留 30 天（`SLIP_DAYS_MAX`），写入时顺带清理过期日期
- 体积：58 技能 × 约 9 个计数器，可忽略
- 读取接口：`slipTotals(prog, { day, days })` 取某窗口的合计，`slipSkills(prog, cause)` 取某错因最集中的技能

**采集时机**：`main.js` 的 `onWrong(cell, st, typed)`，即唯一同时掌握步骤定义与玩家所按数字之处。**不在此处写盘**——计数落在内存的 progress 上，由下一次题目完成时的 `store.save()` 落盘，避免在进位动画里同步序列化整个存档（含最多 3000 条历史）。代价是：中途放弃的那道题的错答不会被保存。

#### 3.1.4 准确性与置信度

分类器是纯函数，可用**构造的错答序列**做单测：给定一道由 `buildSub` 生成的题和一组「按下错误数字」的序列，断言分类结果。

**报告必须显示归因覆盖率**（如「已归因 62 次／共 87 次」），把置信度透明化。

这也正是**先只采集、不展示**的理由：可以先在真实使用中验证准确度，再决定是否展示。

> **已实现**（阶段 2，`25060b8`；④ ⑥ 两张卡片为阶段 4，`4c05ccd`）。实现时发现并修掉三个问题，都不是单测能发现的：星期标签因 `weekday.N` 是周日基准而整体偏一天；`retention()` 遍历全部记录而 `mastery()` 遍历技能树，导致同一页上「掌握 4/58」与「记得 2/5」并列；`layoutActors()` 没有新屏幕的分支，从裸 `requestAnimationFrame` 抛错（不在帧循环的容错范围内），表现为多巴奇停在卡片上挡住内容。最后一处已改为兜底 null-safe，未列出的屏幕不会再把它弄坏。

阶段 4 补上 ④ 哪儿卡住与 ⑥ 下一步后，页面顺序为 ① ② ③ ④ ⑤ ⑥。三处实现细节值得记下：

- **「下一步」的技能是数据驱动的**：取该错因实际最集中的技能（`slipSkills` 的第一名），而不是手写一张「进位错 → 练进位」的对照表。这样建议针对的是孩子真正做错的题，而不是一个类别。
- **没有归因数据时回退到前沿技能**，所以卡片永不空缺，建议是降级而不是消失。
- **「练这个」按钮用事件委托绑定**：报告每次打开都重建，直接绑定会跟着上一个按钮一起失效。

- 新屏幕 `#screen-growth`，结构沿用 `#screen-trophy`（`.tree-head` + 滚动区 + `#growth-back`）
- 标题页入口 `#open-growth` 放在 `.mode-row` 第 4 个，与技能树／奖杯／收藏同组。该行已是 `flex-wrap: wrap`（每个 `min-width: 150px`），390px 屏幕下 4 个按钮仍是两行，不会多占一行
- 分区顺序按「看完能做什么」排列，不按数据类型：

```
① 这周练了多少     分钟 / 次数 / 每日柱状
② 会了什么         掌握 x/58、本周新掌握 n 个、星星 x/290
③ 还记得吗         保持率、生锈技能、上次练习距今
④ 哪里卡住         常错点 Top 3 + 一句具体建议
⑤ 坚持             连续天数、最长记录
⑥ 下一步           一个「练这个」按钮，直接进入对应技能
```

- **导出**：`@media print` 样式表 + 一个「打印 / 存为 PDF」按钮（浏览器原生 `print()`）。不需要新权限、不联网

### 3.4 措辞原则

这四条直接决定这一页是「专业」还是「监控」：

1. **只陈述事实与下一步，不做评价。** 写「跨零退位是最近最常卡住的地方，建议多练 3 年级的退位减法」，不写「掌握较差」；不给等级，不给排名
2. **孩子可以看。** 无密码、无隐藏入口
3. **第一屏是进步。** 「这周新掌握了 2 个技能」放在最上面，「常错点」放后面
4. **不做推送、周报、提醒。** 要看得自己打开
